# Spec: running programs

**Headers:** `<process.h>`, `<stdlib.h>` (`system`)  
**Members:** `system`, `libc16_systeme`, `spawnl`, `spawnv`, `spawnve`, `spawnvp`, `spawnvpe`, `getpid`, each its own member; private members `spawnx` (the spawn functions' core: the mode, the command tail, the extensions), `envblock` (the environment block from `envp`, shared by the `e` forms and `libc16_systeme`), `spawnp` (the `PATH` search) and `dosexec` (INT 21h 4B00h and 4Dh, in assembly); `system`'s member also holds the core it shares with `libc16_systeme`; in each of the small, compact and large libraries (decision 11)  
**Tests:** `tests/process` (run by `tests/run-dos`, in every model)

This is the behavioural spec an implementation is written from (decision 6). It does not describe any existing implementation. `dosexec` is written in assembly: under DOS 2.x, INT 21h 4B00h returns with every register changed, `SS` and `SP` included, which C cannot express.

- `docs/spec/startup.md` ("Command-tail parser"), for the quoting the command tail uses, so that a libc16 child sees the `argv` its parent passed.
- gr-dos/perl16's `docs/M3-RUNTIME-AUDIT.md`, section 6.6, for the proposed contract.
- gr-dos/libc16#31, for `libc16_systeme`: perl16 runs shell commands containing double quotes with `system`, because the spawn functions' quoting reaches `COMMAND.COM` unchanged, and so loses the changes it made to its environment.
- Our own experiments under DOSBox-X (0.09, `tests/run-dos`):
  - 4B00h of a name without an extension fails with error 2: DOS adds none.
  - 4B00h of a missing file, or of a file in a missing directory, fails with error 2.
  - With the environment segment 0 the child gets a copy of the parent's environment; with a segment, a copy of that block, up to its first pair of zero bytes, then the word 1 and the child's full path (`C:\CHILD.EXE`), also for a relative name. A block of just two zero bytes gives the child an empty environment.
  - Under DOSBox-X, `COMSPEC` is `Z:\COMMAND.COM`, and `Z:\COMMAND.COM /C cmd` runs `cmd` but returns 1 (4Dh) whenever it ran a program, whatever that program's exit code, and 0 otherwise. 4300h of `Z:\COMMAND.COM` succeeds.
  - Under DOSBox-X, 4B00h of a missing file whose name ends in `COMMAND.COM` (`\COMMAND.COM`, `C:\X\COMMAND.COM` in a missing directory) does not fail: DOSBox-X runs its own command processor. 4B00h of another missing name (`\FOO.COM`) fails with error 2. (Found by the implementation session.)

## Memory

DOS loads a child into the largest free block. The startup shrinks the program's memory block to end at the top of its stack (`docs/spec/startup.md`), and the heap grows the block as it needs more but never shrinks it, not even when everything is freed (`docs/spec/heap.md`). So a child gets all the memory above the highest point the heap has reached. These functions leave the program's block and the heap as they are: they call no heap function, and a block they take from DOS (the environment of the `e` forms) is freed before they return.

## Common behaviour of the spawn functions

`int spawnv(int mode, const char *path, char * const *argv)`, `spawnve(int mode, const char *path, char * const *argv, char * const *envp)`, `spawnvp(int mode, const char *path, char * const *argv)`, `spawnvpe(int mode, const char *path, char * const *argv, char * const *envp)` and `spawnl(int mode, const char *path, const char *arg0, ...)` run the program `path` with arguments and wait for it to end.

- **`mode`:** `P_WAIT` (0) runs the child and waits for it. `P_NOWAIT` (1), `P_OVERLAY` (2) and any other value fail with `EINVAL`; nothing is run.
- **Arguments:** `argv` is a null-terminated array; `argv[0]` is the child's name by convention and is not passed (DOS gives the child its path itself). `spawnl` takes them as its arguments `arg0`, ... ended by a null pointer, and behaves as `spawnv` with them. A null `argv`, or a null `argv[0]`, fails with `EINVAL`.
- **Command tail:** built from `argv[1]` onward, each argument preceded by one space; no arguments gives an empty tail. An argument that is not empty and contains no space, tab or double quote is copied as it is. Any other argument is written in double quotes, so that the startup's parser gives it back unchanged: inside the quotes, `n` backslashes followed by a double quote are written as `2n + 1` backslashes and the quote, `n` backslashes at the end of the argument as `2n` backslashes, and any other character as itself. The tail is at most 126 bytes, not counting its length byte or the carriage return after it; a longer one fails with `E2BIG` and nothing is run.
- **FCBs:** the parameter block's two FCB pointers point to a blank FCB (drive 0, then eleven spaces, then zeros), so the child's FCBs at PSP offsets 5Ch and 6Ch are blank.
- **Environment:** `spawnv`, `spawnvp` and `spawnl` pass the parent's environment (segment 0). `spawnve` and `spawnvpe` build a block from `envp`: each string in order with its terminating zero, then one more zero; an `envp` with no strings gives two zero bytes. The block is built from `envp` alone, with no use of `environ` (libc16 has none) or `getenv`. A block of more than 32767 bytes fails with `E2BIG`. A null `envp` passes the parent's environment. The block is in memory taken with INT 21h 48h, freed with 49h after the child ends or the call fails; if 48h fails, the call fails with `ENOMEM`.
- **Extensions:** if the last component of the name (after the last `\`, `/` or `:`) contains no `.`, the name with `.COM` is tried, then with `.EXE`. Otherwise the name is tried as it is.
- **`PATH` (`spawnvp`, `spawnvpe` only):** if `path` contains `\`, `/` or `:`, only `path` is tried. Otherwise `path` is tried first (in the current directory), then each element of the parent's `PATH`, in order, with `\` between the element and `path` unless the element ends in `\`, `/` or `:`. Elements are separated by `;`; empty ones are skipped. The search reads `PATH` with `getenv` (`docs/spec/dos.md`), so it overwrites `getenv`'s buffer, and uses the parent's `PATH` even when `envp` has one. A candidate (with its extension) that does not fit in 128 bytes, terminator included, is skipped.
- **Trying a name:** each candidate, with each extension, is run with INT 21h 4B00h. Errors 2 (file not found), 3 (path not found) and 15 (invalid drive) move on to the next one; any other error ends the search, failing with its `errno` as in `docs/spec/io.md` (8 is `ENOMEM`, 11 `ENOEXEC`, 5 `EACCES`). When every candidate fails with 2, 3 or 15, the call fails with `ENOENT`.
- **Result:** the child's exit code: `AL` of INT 21h 4Dh, 0 to 255 (`AH`, how the child ended, is not returned). On failure, -1 with `errno` set; `errno` is unchanged on success.
- **Across the call:** the child inherits the parent's open handles, as DOS does. Before the child runs, the functions write every stdio stream's pending output, as `fflush(NULL)` does (`docs/spec/stdio.md`, "Buffering"), so that the child's output to an inherited handle, or a child reading a file the parent wrote, comes after the parent's earlier output. If DOS does not take all of it, the function runs no child and returns -1, with `errno` from the failed write (as `docs/spec/stdio.md`, "Errors", has it: `ENOSPC` for a short write) and the stream's error indicator set; it frees the environment block it built first, if any, and the output DOS did not take stays pending. (Microsoft C 5.1's leave this to the caller. Streams are unbuffered unless the program calls `setvbuf` or `setbuf`, and a program that does not links nothing for this but `bufhook`'s two pointers.) A failure found before the child would run (an invalid `mode`, a tail too long, no environment block) writes nothing. `dosexec` saves what it needs, `SS` and `SP` included, where it can find them again with every register but `CS` and `IP` changed, and returns with `DS`, `SS`, `SP`, `BP`, `SI` and `DI` as they were (`docs/ABI.md`) and the direction flag clear.
- All are `__cdecl` (`docs/ABI.md`); the pointers are near in the small model and far in the compact and large models. `spawnv`, `spawnve` and `spawnl` link no heap, stdio or `getenv`; the `p` forms link `getenv` and so the startup.

## `int system(const char *cmd)`

Runs the command processor named by `COMSPEC` (from `getenv`), or `\COMMAND.COM` (the root of the current drive) if `COMSPEC` is not set, with the parent's environment and the command tail ` /C ` followed by `cmd` exactly as it is (no quoting), and returns the command processor's exit code (4Dh's `AL`). `cmd` longer than 122 bytes fails with `E2BIG`, as the tail would pass 126. `system` first checks that the command processor exists, as `system(NULL)` does (see below), and fails with `errno` from the DOS error as in `docs/spec/io.md` (`ENOENT` for a missing one) if it does not, before looking at `cmd`; so DOSBox-X's behaviour for a missing `COMMAND.COM` ("Sources") does not hide a missing command processor. If the command processor cannot be run, `system` returns -1 with `errno` set as for the spawn functions (`ENOENT` for a missing one). No extension is added and no `PATH` search is made.

`system(NULL)` runs nothing and returns 1 if the command processor exists (INT 21h 4300h succeeds and it is not a directory), else 0.

The exit code is the command processor's, not necessarily the command's: DOSBox-X's `COMMAND.COM` returns 1 whenever it ran a program and 0 otherwise (see "Sources"). C89 leaves the value implementation-defined.

`system` links `getenv` and so the startup, and no heap or stdio.

## `int libc16_systeme(const char *cmd, char * const *envp)`

libc16's own extension (#31): `system` with an environment. It runs the command processor as `system` does, with the command tail ` /C ` followed by `cmd` exactly as it is, byte for byte: no splitting into words, quoting or escaping, so double quotes, backslashes, tabs, `%`, redirection and pipes reach the command processor as the caller wrote them. The child's environment is built from `envp` as `spawnve` builds it ("Common behaviour of the spawn functions", "Environment"): each string in order, then one more zero; an `envp` with no strings gives an empty environment; a null `envp` passes the parent's environment, so that `libc16_systeme(cmd, NULL)` is `system(cmd)`.

- **The command processor:** named by the parent's `COMSPEC` (from `getenv`), or `\COMMAND.COM` if the parent has none, as for `system`. A `COMSPEC` in `envp` is passed to the child but does not choose the command processor, as `spawnvpe` searches the parent's `PATH` whatever `envp` holds.
- **`cmd` null:** runs nothing, builds no environment and returns what `system(NULL)` returns: 1 if the command processor exists, else 0. `envp` is not looked at.
- **Order of checks**, each failing with -1 and `errno`, with nothing run and no memory kept: the command processor exists and is not a directory (`errno` from the DOS error, `ENOENT` for a missing one), as for `system`; `cmd` is at most 122 bytes (`E2BIG`); the environment block is at most 32767 bytes (`E2BIG`); INT 21h 48h gives memory for it (`ENOMEM`). Then the command processor is run; if it cannot be, -1 with `errno` as for `system`.
- **Result:** the command processor's exit code (4Dh's `AL`), as for `system`; `errno` is unchanged on success. The environment block is freed (49h) after the child ends.
- **Across the call:** as for `system` and the spawn functions: the program's memory block and the heap are left as they are, the child inherits the open handles, and the streams' pending output is written first.
- `__cdecl`, declared in `<process.h>`. It links `getenv` and so the startup, and no heap or stdio. A program that calls `system` alone does not link `libc16_systeme`, and one that calls `libc16_systeme` does not link the spawn functions' argument quoting. The implementation should share `system`'s and `spawnve`'s code where it can rather than repeat it.

## `int getpid(void)`

Returns the program's PSP segment (`_psp`). It is unique among the programs running at the same time: a child's PSP is in memory the parent's block does not contain. Links the startup.

## `<process.h>`

Declares the spawn functions, `system`, `libc16_systeme`, `getpid`, and `P_WAIT` (0), `P_NOWAIT` (1) and `P_OVERLAY` (2). `<stdlib.h>` declares `system` too.

## Tests

`tests/process`, in every model, with `CHILD.EXE` (`tests/process/child.c`), a libc16 program that prints, one per line: with `TAIL` in its environment, `tail[` its command tail from PSP offset 81h, byte for byte `]`; `name[` its full path (from after its environment) `]`; `arg[` each argument `]`; with `-e` as its first argument, `env[` each environment string `]`; with `-g NAME`, `val[` the value of `NAME` `]`, or `val(null)`; with `-f`, `fcb[` its first FCB's drive (a digit) and the 11 name bytes `]`. When its first argument is `/C` (run as a command processor), the options are looked for after it. It exits with the value of its last argument if that starts with a digit, else 0.

- `process`: exit codes (0, 7, 255); arguments with spaces, tabs, double quotes, backslashes and empty ones, seen exactly by the child; the 126-byte limit with and without quoting (`E2BIG`, nothing run); blank FCBs; the extension rule (`CHILD` runs `CHILD.EXE`, `KID` finds `KID.COM` before `KID.EXE`); the `PATH` search, with missing and empty elements and an element ending in `\`, the current directory first, no search for a name with a `\` or for `spawnv`, and the parent's `PATH` for `spawnvpe`; an `envp` the child sees, an empty one, a null one (inherits) and one over 32767 bytes (`E2BIG`); inheritance of a variable the cases set; `P_NOWAIT`, `P_OVERLAY` and 99 (`EINVAL`); a null `argv`; missing programs (`ENOENT`); `errno` unchanged on success; the program's memory block and the largest free block the same after each call; `getpid` equal to `_psp` and to INT 21h 62h.
- `nopath`: `spawnl`, `spawnv` and `spawnve` alone, so that `tests/check-members` checks they link no `getenv`, heap or stdio.
- `system`, run four times by the cases: with `COMSPEC` set to `C:\CHILD.EXE` (the exit code passes through; the tail is ` /C ` and the command; `system(NULL)` is 1; 122 and 123 bytes); with `COMSPEC` unset (`system(NULL)` is 0 and `system` fails with `ENOENT` until the test copies `CHILD.EXE` to `\COMMAND.COM`, then runs it); with `COMSPEC` naming a directory (`system(NULL)` is 0 and `system` fails); and with DOSBox-X's `Z:\COMMAND.COM` (a command with redirection runs, and its output file has the child's output).
- `systeme`, run four times as `system` is, with `LIBC16` set to `OLD`: with `COMSPEC` set to `C:\CHILD.EXE`, the command tail byte for byte (`CHILD.EXE` prints it when `TAIL` is in its environment) for a command with quotes, escaped quotes, backslashes, an empty quoted word, a tab, `%`, `<`, `>`, `|` and `;`, the parent's `COMSPEC` used when `envp` names another, the child's environment changed, added to, deleted from, empty and inherited (null `envp`), the exit code, `cmd` null with and without `envp`, 122 and 123 bytes, an environment over 32767 bytes, and `ENOMEM` with DOS's largest free block taken, each failure running nothing; with `COMSPEC` unset, even with `COMSPEC` in `envp` (`ENOENT`); with `COMSPEC` naming a directory; and with DOSBox-X's `Z:\COMMAND.COM`, a command with a quoted argument and redirection, whose child sees a variable that only `envp` holds.
- `bufkid`, with `COMSPEC` set to `C:\CHILD.EXE`: fully buffered standard output, then `spawnl`, `system` and `libc16_systeme`, and a line-buffered partial line, then `spawnl`; each child's output comes after what the parent wrote before the call (`docs/spec/stdio.md`, "Buffering").
- `buffail`, with `COMSPEC` set to `C:\CHILD.EXE` and `tests/stdbuf/wrhook.asm`: a buffered file stream whose writes fail (DOS error 5) or write short; `spawnl`, `spawnve`, `system` and `libc16_systeme` each return -1 with `errno` `EACCES` or `ENOSPC` and the stream's error indicator set, and run no child (no child output); `spawnve`'s and `libc16_systeme`'s environment blocks are freed (DOS's largest free block is unchanged); with the writes let through, each runs its child.
- 8086 instructions only (`tests/check-8086`).
